# ADR-0012 — Sync through your server (M4b)

- Status: accepted (owner, 2026-11-12: "Yes, sync after editor"). Builds on
  [ADR-0009](0009-browser-storage-and-backup.md) (backup, the amendment's sync rules),
  [ADR-0011](0011-own-storage-server.md) (the server: a strong ETag per file, `If-Match` /
  `If-None-Match` under a lock per path, `PROPFIND` depth 0 or 1) and
  [ADR-0003](0003-file-format.md) (paths come from IDs).
- Rule 1 of AGENTS.md is the rule of this milestone: **sync never loses a word**.

## Context

Two or more devices keep one workspace. Each writes locally first (the save pipeline: journal,
compare-and-write), and may be offline for days. The server is a plain WebDAV folder, so it
can offer exactly one atomic thing: "write this file only if its ETag is still X". Everything
else (what changed, who wins, what a delete means) the clients must decide from what they
remember and what they see.

## The model

**`current/` on the server is the shared copy.** A device keeps, per file, a **base**: the
server ETag it last agreed on, and the hash of the bytes that were then on both sides. It lives
in the device database (never in the workspace), beside the backup state.

**A round** (one device, one pass over the folder; pull and push together):

1. Let pending saves land (`flush`), then hash every local file (**local**).
2. List `current/` by walking folders with `PROPFIND` depth 1 (**remote**: path → ETag).
3. For every path, compare three things: remote ETag and local hash against the base.

| Local vs base | Server vs base      | Action                                                                                                         |
| ------------- | ------------------- | -------------------------------------------------------------------------------------------------------------- |
| same          | same                | nothing                                                                                                        |
| changed / new | same / absent       | **push**: `PUT` with `If-Match: <base ETag>` (`If-None-Match: *` for a new file)                               |
| same          | changed / new       | **pull**: download, apply through the session                                                                  |
| changed       | changed             | download theirs; equal bytes: adopt. Different: **conflict** (below)                                           |
| new           | new, no base        | same as the row above                                                                                          |
| same          | gone, tombstone     | another device deleted it: **delete here** (a version first)                                                   |
| same          | gone, no tombstone  | nobody decided it: the server lost it, so it **goes back up**                                                  |
| changed       | gone                | delete against edit: **the edit wins**, pushed back as a new file                                              |
| gone          | same                | **delete there**: `DELETE` with `If-Match`, and leave a tombstone                                              |
| gone          | changed             | delete against edit: **the edit wins**, pulled back                                                            |
| gone          | gone                | forget the base                                                                                                |

A `412` on any write means someone wrote in between: that file is left, and the round starts
again from the listing (at most four passes, then it stops and retries later). Nothing is ever
written to `current/` without `If-Match` or `If-None-Match`.

**A conflict never overwrites.** Both texts are kept: the device's own text stays in the file,
and the server's text is saved as a copy beside it, `scn_x (Aurelia copy 3fa9c0d1).md` (the
first eight letters of the copy's hash). The copy is an ordinary workspace file that goes to
the server and to every device, so all of them end up with both texts, and the session shows it
as "two versions of one file" (the conflicted-copy flow of M2: *Keep the text in the scene* / *Use the
set-aside text* when synced, the other one set aside in `.aurelia/conflicts/`, never deleted). The name comes from the
content, so two devices that make the same copy make the same file, and different texts can
never share a name.

**Deletes are tombstones, written before the delete.** A device that deletes a file first writes
`path → hash of the deleted bytes` into `backup.json` (compare-and-write), then removes the file
with `If-Match`. If the file is gone from the server and a tombstone names it, a device whose
copy is unchanged since it last agreed deletes it too, however far behind it is. If the file is
gone and **no** tombstone names it, nobody decided it (a volume that came back empty, an admin's
file manager): the file goes back up, whether one file or all of them. A refused `DELETE` (the file
changed meanwhile) leaves its tombstone, which means nothing while the file exists. A tombstone is
dropped when the path is written again.

**A file this device has no record of is the author's.** A file with no base (a restored database,
a device that never synced it) is pushed, never removed for a tombstone: a deleted file the author
brought back is words. The price, accepted: a device that never synced a file can bring a deleted
one back.

**Moves follow stable IDs.** An entity's path is built from its ID (ADR-0003), so moving a
scene to another chapter, or renaming anything, edits the file in place: the same path with
other frontmatter. That is an ordinary edit to the sync. A file that really changes path (an
outside tool moved it) is a delete plus a new file: both texts survive, and the loader already
shows two files with one ID to the author instead of choosing.

**A version before remote changes.** A round that is about to overwrite or delete a local file
first saves a version of the whole workspace to `versions/` (`…_before-sync.zip`, kept a day, then
thinned like hourly versions). Every such round saves one, however recent the last was, unless the
workspace is exactly what the last one holds (a hash of every file's hash), so a retried round piles
up nothing. If that upload fails, the round stops before touching a file.

**The workspace file.** When `aurelia.json` differs on both sides and only its **lists** differ
(the order of the universes, say), they are put together by union: no copy, no orphaned scene. Any
other difference is a conflict and keeps both texts. **Derived files** (M3a: a book's `OUTLINE.md` and
the `outline` cache inside its `book.json`) are not the author's text: a conflict on them makes no copy.
Mine goes up, and after any round that brought files in or sent them out the device writes them again from
the scenes' frontmatter (`regenerateOutlines`), which the next round sends. Any other difference in
`book.json` (its title) is the author's and keeps both. The trash (`.aurelia/trash/**`) and the set-aside
texts (`.aurelia/conflicts/**`) sync like any file.

**Version names.** A version's name carries the first eight letters of its zip's hash
(`2026-11-12T18-30-05~3fa9c0d1_before-sync.zip`), so two versions of different text made in one second
are two files and none is dropped. Older names still read.

**A lost server while a device is behind.** After a server loses its files the devices put theirs
back. A device that was behind and goes first puts up older text, and a device whose copy was
unchanged since it last agreed (but newer than that) takes it. The text it overwrites is in the
version saved just before, which is never skipped for being recent, and a restore can open it.

## Applying remote changes: through the session

The engine never writes workspace files itself. It hands changes to the open session
(`applyRemote`), which hands each to the save pipeline (`receive`):

- It runs after any save in flight for that file, and is **compare-and-write**: the file must
  still hold the bytes the base says (else it is *deferred* — the next round sees a local change
  and takes the conflict path above).
- Then the session reads the files again, so the open scene updates in place.
- **Unsaved edits** in that file: the arriving text goes to the file, and the author's text
  stays on screen as a conflict (the M2 compare dialog: *Keep mine* / *Use the file's version*,
  the loser saved as a copy). The journal still holds it.
- Read-only, still settling after another tab took over, or open in another tab: no round runs
  and nothing is applied.

## When

Pull on open and every three minutes (`SYNC_POLL_MS`) and when the window gets focus or comes
back online; push a minute after the author stops typing and when the tab is hidden (the backup
debounce). Offline: nothing is queued separately. The base is stored, so "what is waiting" is
always *local files that differ from the base*, found again by the next round. The status bar
says "Offline — changes waiting". A `401` or a login redirect pauses with "sign in again".

## `backup.json` and backup, with sync on

The manifest gains one optional member, still `schemaVersion: 1`:

```json
"sync": { "devices": { "<deviceId>": { "name": "Safari on iOS", "at": "…" } },
          "tombstones": { "<path>": { "hash": "…", "at": "…" } } }
```

- `files` still lists `current/` with hashes, so **Restore works unchanged**. A synced round
  rewrites it from what it knows `current/` holds, so one that fell behind (a device died after
  its uploads) is put right by the next round of any device. A restore that meets a half-done round
  fails its hash check and says so; it never opens a mixed copy.
- **The single-writer rule becomes a set.** Backup says "another device wrote here: ask" because
  one folder has one owner. A manifest with `sync` has the set `devices`: a device that chose
  sync joins it and may write; it is never asked. Only the device that owns the folder (the
  backup's single writer) can turn it into a synced one. A device meeting a plain backup of
  another device is asked as before (*Keep both* / *Use the backup here*).
- **One engine, two modes.** With sync on, the sync round replaces the backup upload (they would
  write the same `current/`); the hourly versions, the versions before a risky choice, retention,
  retries and "sign in again" are the same code. Turning sync off leaves the device list and goes on backing up, to a folder of the device's own
  (the shared one has other devices writing in it); turning it on again returns to the shared folder
  with what was agreed there still remembered.
- A device in plain backup mode that rewrites a manifest keeps its `sync` member as it found it.

## Turning it on, and a second device

- **First device:** "Keep this workspace in sync on this device" (Backup screen). If it already
  backs up to the folder, its manifest and uploaded hashes seed the base (no download); else the
  first round compares each file once.
- **Second device:** *Restore from a backup* offers "…and keep it in sync" for a folder whose
  manifest has `sync` and for **the latest** copy. The restored copy keeps the **same workspace
  ID** as the server folder, and starts with each file's base set from the very GETs it was
  restored from (ETag and hash), so its first push can only be an `If-Match` against what it
  restored. M2b gives a restore a new ID when the device already knows the old one, because an
  old copy could otherwise back up over `current/`. Sync does not need that, because it never
  writes without `If-Match`; but the device state is keyed by workspace ID, so **a synced restore
  is refused when this device already has a workspace, a recent, or backup state with that ID**
  ("Open it and turn sync on there"), and an ordinary restore still gets a new ID.
- **A device that backs up into a folder that others sync** is asked, in plain backup mode, to *Join the
  sync* (it turns sync on over the workspace it has, which keeps its ID; where both changed a file,
  both texts are kept) or to *Keep both* (its own folder). It is never offered a restore as a new copy.

## What it does not do

- It does not merge texts (no three-way merge of a scene): a conflict keeps both, whole. The one exception is the lists of `aurelia.json`.
- It leaves a remote file that is not UTF-8 text alone (never written, never deleted).
- A tombstone is kept until the path is written again; a device that has been offline for a
  year still has its base, so it is never mistaken for a new device, and still follows a delete.
- Sync through Google Drive, OneDrive, S3 and end-to-end encryption stay in M10.

## Tests

Property tests drive two and three devices through random edits, creates, deletes (one file and
most of a workspace), moves, offline periods and rounds against the in-memory WebDAV, with the real
session, pipeline, engine and WebDAV client. A second kind of run overlaps the devices' rounds and
types between the moment a round reads the files and the moment it applies what it fetched
(saved or not); a third moment of calm has the server lose its files. Invariants: no word ever
saved is lost (every token ends up in some file), all devices converge to identical files once
quiet and online, a deleted file does not return unless edited elsewhere (calm runs), no write
reaches `current/` without a precondition, and a restore of what the devices agreed on passes its
hash check.
